# OpenCray 产品定位修正版草稿

说明：本文件用于沉淀已经通过代码核实的产品定位与写作边界，供正式参赛文档回填，不作为最终提交稿。

## 一、当前可成立的产品定位

OpenCray 更准确的定位，不是旧的“工作台式”表述，而是：

- 主定位句：越用越懂用户的手机端私人助理
- 核心关键词：个性化协作
- 面向人群：普通用户和专业用户
- 产品取向：低门槛，但保留高上限

更适合写进正式稿的一句话版本：

> OpenCray 是一个可直接部署在手机端、权限可控、具备个性化协作能力的私人助理。

补充展开时，可以落成下面这段：

> 本作品希望把手机端私人助理做成长期可用的软件，而不是一次性的问答入口。普通用户可以直接用它完成资料搜集、文件整理、问答和内容撰写；专业用户也可以进一步开放路径权限、调用 Python、接入联网搜索和技能扩展，处理更复杂的任务。

## 二、已经通过代码核实的几项核心能力

### 1. 权限可控，不是口头描述

代码中已经有完整的安全设置体系，正式稿可以稳写以下内容：

- 系统默认采用偏保守的权限配置
- 用户可以粗粒度选择三档自动化模式：`SAFE / AUTO / DEV`
- 用户也可以细粒度配置文件修改、文件删除、Shell 命令等策略：`Inherit / Ask / Allow / Block`
- 外部访问不是默认全开，公共路径需要单独授权
- 已支持的公共路径包括照片、下载、文档、录音
- 高风险操作会进入审批流程，并以橙色高亮提醒用户
- 用户也可以根据任务需要放宽审批，减少中途打断

这一部分更适合写成“用户主权”和“安全边界”：

> OpenCray 并不默认替用户做风险判断，而是把关键权限的决定权交给用户。系统默认保守，高风险操作先审批；当用户明确需要更高自动化程度时，也可以按档位或按工具逐步放开。

### 2. 个性化协作机制已经落地，不是概念词

正式稿建议不要直接把 `Memory` 和 `Soul` 当成独立卖点硬写，而是统一成“个性化协作机制”，再拆成两层：

- 记忆系统：负责保存用户偏好、工作区事实、持续性指令和阶段性承诺
- 协作风格系统：负责把长期偏好和当前关系状态叠加到交互风格里

代码中已核实的事实：

- 记忆有 `USER / WORKSPACE / SESSION` 三层作用域
- 记忆类型包括用户偏好、项目事实、持续性指令、任务承诺
- 不同类型记忆有不同保留策略，不是“什么都记”
- 记忆本地存储在应用目录中，未依赖云端记忆
- 协作风格会结合工作区配置和记忆叠加，不是固定预设
- 系统会根据偏好与关系状态调整称呼、语气、详细程度等交互细节

这一部分适合写成用户能感知到的效果：

> 软件会在本地逐步积累用户偏好、持续性要求和任务上下文，再把这些内容用于后续协作。用户给它起名字、要求它保持某种说话方式、提醒它别动某些内容，这些都可以在后续会话中延续下来。久而久之，协作成本会下降，使用体验也会更接近固定搭档。

### 3. “越用越懂用户”有明确技术支撑

这句话不是宣传语，代码里至少有三层支撑：

- 长期偏好记忆：如称呼、显示名、交互偏好、详细程度
- 工作区与会话事实记忆：用于保留任务相关上下文
- 协作风格叠加：把偏好与关系状态投射成实际对话风格

正式稿可以这样写：

> 本作品把“越用越懂用户”落实成分层记忆和协作风格叠加机制。系统既能保留长期偏好，也能在当前任务中维持短期事实，并把这些信息用于后续对话和执行过程，减少用户反复说明的负担。

### 4. 一条龙任务链已经可写

代码已支持计划、执行、审批、继续执行这条链路，不需要再写成“未来设想”。

可稳写的点：

- Agent 会维护任务计划与待办状态
- 同一时刻最多只有一个进行中的待办项
- 聊天页会展示 TODO、审批卡片、继续执行入口
- 高风险步骤被用户审批后，任务可以继续推进
- 用户看到的是一条连贯的任务链，内部则是分阶段完成

适合正式稿的写法：

> OpenCray 的任务执行不是单轮回复，而是可持续推进的任务链。系统会先形成计划，在执行中根据权限要求插入审批，再在用户确认后继续推进，最后把结果回收到会话和工作区中。

### 5. 手机端文件处理可以作为主场景来写

文件页已经支持下列能力：

- 浏览目录
- 搜索
- 新建文件夹与文本文件
- 文本预览与编辑
- Markdown 预览
- 图片预览
- 分享
- 复制、移动、重命名、删除

因此正式稿完全可以把“在手机上直接处理文件”写成主卖点之一，而不必再写成附属功能。

### 6. Python 与联网搜索链路可以写，但措辞要收住

当前已经可以稳写：

- Agent 已支持正式工具 `python_exec`
- Python 执行限制在工作区内
- 工作区侧会管理 Python 环境与依赖
- 已有联网搜索配置页和搜索 provider 接入能力
- Agent 可以把搜索、文件处理和 Python 脚本串成同一条任务链

更稳妥的表述边界：

- 可以写“支持通过 Python 链路处理文档并输出工作区产物”
- 可以写“支持联网搜索配置与信息搜集”
- 不建议写成“稳定内置一键导出 docx 按钮”
- 不建议把 Android 内嵌 Python 说成已经完全打通到没有边界

## 三、与豆包、Kimi 的对标角度

正式稿里不建议把竞品分析写成模型参数比较，直接比较产品形态和使用路径更稳。

建议维度：

| 维度 | 豆包 | Kimi | OpenCray |
| --- | --- | --- | --- |
| 产品形态 | 通用智能助手 | 通用 AI 助手，长文本解析与深度研究能力较强 | 手机端私人助理 |
| 手机本地文件处理 | 以平台内上传与交互为主 | 以对话、资料解析和研究入口为主 | 可直接浏览、编辑、分享本地工作区文件 |
| 权限控制 | 平台预设为主 | 平台预设为主 | 用户可按档位、路径、工具配置权限 |
| 个性化协作 | 可定制智能体与交互风格 | 面向特定任务代理 | 记忆系统与协作风格系统联动 |
| 能力上限 | 以平台功能为主 | 文档与研究链路较强 | 可串联文件、联网搜索、Python 与技能扩展 |

一句话概括差异：

> 豆包和 Kimi 更偏平台型助手，OpenCray 更强调在手机本地把权限、文件、工具和长期协作放到同一套交互里。

## 四、正式稿建议保留的表达

### 1. 需求分析可直接使用的表述

> 现有智能助手已经能完成问答、创作和资料整理，但在手机端，本地文件处理、权限审批、工具调用和长期个性化协作往往是割裂的。OpenCray 的目标，是把这些能力收拢到同一个 Android 应用中，让用户在手机上就能发起任务、授权路径、查看过程、处理文件并保留长期偏好。

### 2. 亮点概括版

- 手机端可直接部署
- 本地文件处理能力完整
- 权限默认保守，配置可细可粗
- 支持联网搜索和 Python 执行链路
- 具备记忆系统与协作风格系统
- 能把任务以一条链路连续推进

### 3. 总结段可用表述

> 本项目的核心收获，不是多做了几个页面，而是在手机端把“低门槛”和“高上限”放到了同一套产品里。普通用户可以把它当成私人助理使用，专业用户又能在明确授权后把它扩展成更强的任务执行工具。

## 五、正式稿里不要写进去的内容

下列尚未完成的扩展方向，当前不要写入正式参赛文档：

- 云端沙箱类扩展
- 数字映射类扩展
- 多智能体协作类扩展

下列表述也不要写得过满：

- Android 内嵌 Python 已经完全无边界打通
- 稳定内置一键生成 `docx`
- 仅面向专业用户
- 产品主轴是 `Chat / Files / Skills / Settings`

## 六、当前结论

正式稿的主轴已经可以明确：

- 它是手机端私人助理，不是工作台式产品
- 它覆盖普通用户和专业用户，不只服务开发者
- 它的第一关键词是个性化协作
- 它的差异点不是“功能堆叠”，而是手机端本地部署、权限可控、长期协作和高可塑性任务链

如果后续继续补写正式稿，优先顺序应当是：

1. 先把需求分析和竞品表改正。
2. 再把第二章、第三章的主轴改成“权限 + 个性化协作 + 任务链”。
3. 最后再修第五章和第六章，让整体都回到“私人助理”定位上。
